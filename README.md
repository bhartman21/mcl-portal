# MCL Portal

Angular 21 + Bootstrap 5 + Firebase portal for the **Marine Corps League, Department of Florida (DoF)**: portal shell (sign-in, roles, detachment directory), **Ad Book Studio** (Phase 1), and the **VAVS Service Tracker** (Phase 2).

- **Repo:** https://github.com/bhartman21/mcl-portal (public: never commit keys or real config)
- **Firebase project:** `mcl-portal` is **planned but not created yet**. Default Hosting URL once created: `https://mcl-portal.web.app`. If the id is taken, record the real id in `.firebaserc` and the `FIREBASE_PROJECT_ID` secret.
- **Planning docs:** [PROJECTPLAN.md](./PROJECTPLAN.md) · [ARCHITECTURE.md](./ARCHITECTURE.md) · [ROLES_AND_PERMISSIONS.md](./ROLES_AND_PERMISSIONS.md) · [STYLE_GUIDE.md](./STYLE_GUIDE.md) · [OPEN_QUESTIONS.md](./OPEN_QUESTIONS.md). See [Planning docs](#planning-docs) below.
- User and admin guides live in [`docs/`](./docs/) (maintained by D.O.T.).

## Quick start: local demo mode (no Firebase)

```bash
npm ci
npm start            # ng serve → http://localhost:4200
```

The committed environment files hold **placeholders only**, so the app starts in **Local Demo Mode**: a "Local Demo Mode" badge shows in the header, and the sign-in page offers preview accounts (member, detachment VAVS rep, ad approver, department admin). Nothing is sent to a server; data lives in this browser's localStorage.

## Run against the Firebase emulators (recommended for development)

```bash
npm run config:emulators   # writes gitignored src/environments/environment.local.ts (project demo-mcl-portal)
npm run emulators          # Auth :9099, Firestore :8080, Storage :9199, Emulator UI :4000
npm run start:firebase     # in a second terminal → http://localhost:4200
```

Email sign-in links are not emailed by the Auth emulator. Open the Emulator UI (http://127.0.0.1:4000 → Authentication) or the emulator log to get the link.

## Run against a real Firebase project

1. Copy `.env.example` to `.env.local` (gitignored) and fill in the web app config from Firebase console → Project settings → Your apps.
2. `npm run config:env` writes the gitignored `src/environments/environment.local.ts`.
3. `npm run start:firebase` (dev server) or `npm run build:firebase` (production build into `dist/mcl-portal/browser`).

The same variables can come from the shell environment instead of `.env.local`: `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, `FIREBASE_STORAGE_BUCKET`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_APP_ID`. Optional: `APP_PRODUCTION=false`, `ENABLE_GOOGLE_SIGN_IN=true` (Google sign-in is off by default; the plan says it "may be added later").

## Lint, tests, build

```bash
npm run lint                         # angular-eslint (TS + templates + a11y)
npm test -- --watch=false            # unit tests (Vitest via @angular/build:unit-test)
npm run test:rules                   # Firestore + Storage security-rules tests in the emulators (needs Java)
npx ng build --configuration production
```

`npm run test:rules` runs `firebase emulators:exec --only firestore,storage --project demo-mcl-portal "vitest run --config vitest.rules.config.mts"`. Tests live in `rules-tests/`; `rules-tests/helpers.ts` provides personas (`USERS.member`, `USERS.deptAdmin`, …), `seed()`, `asUser()` and `asGuest()` so new suites (for example the Ad Book fixes) are a new `*.rules.test.ts` file.

## Deploy (GitHub Actions → Firebase Hosting)

> **Activation pending:** the workflows are currently staged in [`ci/github-workflows/`](./ci/github-workflows/) because the token that opened the Phase 0 PR lacked GitHub's `workflow` scope. Move them to `.github/workflows/` to turn them on (see that folder's README).

- `.github/workflows/ci.yml` runs on every PR and push to `main`: `npm ci`, lint, unit tests, rules tests, production build.
- `.github/workflows/deploy.yml` runs on push to `main` (and manually). It writes `environment.local.ts` from secrets, runs `npm run build:firebase`, then `firebase deploy --only hosting,firestore:rules,storage`. **Until every secret below exists, the job skips with a notice instead of failing.**

Deploys run as a dedicated service account named **`github-deploy`** (the same name the Firebase setup guide uses).

Required repository secrets (Settings → Secrets and variables → Actions):

| Secret | Value |
|--------|-------|
| `FIREBASE_SERVICE_ACCOUNT` | JSON key for the `github-deploy` service account (roles: Firebase Hosting Admin and Firebase Rules Admin, or Firebase Admin). Service Account User isn't needed because Hosting has no rewrites to a function or Cloud Run. |
| `FIREBASE_PROJECT_ID` | e.g. `mcl-portal` |
| `FIREBASE_API_KEY` | web app `apiKey` |
| `FIREBASE_AUTH_DOMAIN` | e.g. `mcl-portal.firebaseapp.com` |
| `FIREBASE_STORAGE_BUCKET` | e.g. `mcl-portal.firebasestorage.app` |
| `FIREBASE_MESSAGING_SENDER_ID` | web app `messagingSenderId` |
| `FIREBASE_APP_ID` | web app `appId` |

Manual deploy from a workstation: `npx firebase login`, then `npm run config:env && npm run build:firebase && npx firebase deploy --project <id>`.

## One-time Firebase project setup (owner)

1. Create the Firebase project (preferred id `mcl-portal`). Do **not** reuse `mcl-rack-builder`.
2. Add a **Web app**; copy its config into the GitHub secrets above (and your `.env.local`).
3. **Authentication → Sign-in method:** enable **Email/Password** and its **Email link (passwordless sign-in)** option.
4. **Authentication → Settings → Authorized domains:** keep `mcl-portal.web.app` / `mcl-portal.firebaseapp.com`; add `localhost` for local testing (new projects no longer include it by default) and any custom domain later.
5. Upgrade to the **Blaze** plan (required for Cloud Storage since Feb 3, 2026, and for more than 5 sign-in link emails/day), set the $20/month budget and shutoff from ARCHITECTURE.md "Pricing plan and cost cap", then create **Cloud Firestore** (production mode) and **Cloud Storage** (default bucket), both in `us-east1`.
6. Create the deploy service account key and add `FIREBASE_SERVICE_ACCOUNT`. Storage rules use cross-service `firestore.get()`, which needs a one-time permission grant: do the first Storage rules publish interactively (`npx firebase deploy --only storage --project <id>` after `firebase login`, or paste `storage.rules` in the console) and accept the prompt, so the non-interactive CI deploy doesn't stop on it.
7. Push to `main` (or run the Deploy workflow manually).

## First admin bootstrap (one time)

There are no hard-coded admin emails. Roles live in `users/{uid}` and only an existing admin can change them, so the very first admin, the **site administrator** (`siteAdmin`, Billy at launch), is promoted by hand once:

1. Open the deployed site and sign in with the email link. This creates `users/{your uid}` with `roles: ['member']`.
2. In Firebase console → Firestore → `users` → your document, edit `roles` to `["member", "siteAdmin"]` and make sure `status` is `"active"`. (The console bypasses security rules; this is the only time roles are edited outside the app.)
3. Reload the portal. On first admin load the app writes `settings/registration` (`mode: 'open'`) and seeds the DoF `detachments` directory (#54 = Morris F. Dixon Jr.; S/Sgt Ted Archambault = #819; full list of 51 detachments). If the directory is still empty, use **Admin → Detachment Directory → Seed DoF Detachments**.
4. From then on, assign every other admin from **Admin → Users & Roles**. Each grant or revoke is written to `audits` (who, when, target user, before/after roles).

### Admin grant hierarchy (decided Nov 14, 2026)

| Signed-in admin | May grant and revoke |
|-----------------|----------------------|
| `siteAdmin` | every role, including `siteAdmin`, `nationalAdmin`, `departmentAdmin` |
| `nationalAdmin` | `nationalAdmin`, `departmentAdmin`, and all non-admin roles |
| `departmentAdmin` | `departmentAdmin` and all non-admin roles |

- `siteAdmin` has every permission of `nationalAdmin` (admin pages, settings, detachments, ad sizes, Ad Book review, VAVS).
- Nobody can change their own roles or status, and an admin cannot edit, suspend, or delete a user who holds a role they could not grant (revoke rules are **inferred**, see OPEN_QUESTIONS #17).
- A role or scope change is a batched write of `users/{uid}` (with a new `roleAuditId`) plus `audits/{roleAuditId}`; `firestore.rules` rejects either half on its own, so audits cannot be skipped or forged.

## Implementation notes

- **Auth:** Firebase email sign-in link only (decided). If the link is opened on another device or browser, the sign-in page asks the user to re-enter their email. Guards (`authGuard`, `activeUserGuard`, `roleGuard`) wait for the initial auth state, so refreshing a protected page does not bounce to `/sign-in`.
- **Registration mode:** `settings/registration.mode` `open` (default) → new users are active members; `approval` → new users are `pending` and cannot write until an admin approves them. Enforced in `firestore.rules`, not just the UI.
- **Firebase SDK (deviation):** the plan lists `@angular/fire`. `@angular/fire` 21 requires `firebase@^12`, while this app already uses `firebase@13`, so the app keeps the modular Firebase JS SDK behind `FirebaseService` (Auth, Firestore, Storage). Revisit when `@angular/fire` supports `firebase@13`.
- **Ad Book data (issue #4):** with a Firebase config, ads, event books, ad sizes, Ad Book audits, and self-approval notifications live in Firestore, and ad images upload to Storage at `ad-images/{uid}/{adId}/{file}` (JPEG/PNG/WebP, under 10 MB; PDF and Word files are converted to PNG first). Firestore stores only `imagePath`; the app resolves a display URL at runtime, so no image or data URL is saved in Firestore. Screens update live (approvers on other computers see new submissions). The first approver or admin to open Ad Book on a fresh project writes the four seed ad sizes. The batched writes live in `src/app/core/ad-book/ad-book-firestore.ts` and are the same ones the emulator tests run (`rules-tests/ad-book-writes.rules.test.ts`). Local demo mode (no Firebase config) still keeps Ad Book data in this browser only.
- **Book placement:** an approver places an approved ad in an **open** book; the ad records `bookId` and the book lists it in `adIds`, written together and checked by the rules. An ad sits in one book at a time. A locked or printed book takes no new placements and its ads can't be removed or reordered until it is reopened. Nobody places or removes their own ad (another approver must), and anyone who has an ad in a book can't reorder that book, because page order follows `adIds`. The book keeps `ownerCounts` (uid → number of their ads in it) so the rules can check this.
